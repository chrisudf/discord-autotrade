## 素材
- 整晚终端日志：`{{LOG}}`
- 数据库摘要（当晚开仓 / 事件 / 下单 / 原始消息 / 未平持仓，时间已转成本机本地时区）：`{{DIGEST}}`
- 代码库：`{{PROJ}}`（要看解析逻辑就读 `autotrade/parsing/signal_parser.py`、`autotrade/listener/`）

先把 `{{DIGEST}}` 整个读完，再读日志。日志可能有几千行，别一次全灌进来 —— 用 grep 按下面的关键标记切片，只在需要确认上下文时才读原文附近几十行。

两个格式上的坑，先记住：
- 摘要是 `列 | 列 | 列` 的一行一条记录；原文里的换行已被压平成 ` / `。
- **喊单机器人每条消息都会发中英两遍**（相隔 2-4 秒，msg_id 不同）。统计条数时按语义去重，别把同一个信号算成两条。

## 要回答的问题
按重要性从高到低：

1. **漏掉的信号**（最重要）。grep `Parse failed` 和 `[parser] no signal`，逐条判断：哪些其实是**有效的开/平仓信号但解析器没认出来**？哪些确实只是闲聊/播报（例如喊单员的行情评论、盘前提醒、@everyone 通知），属于正确忽略？把前者单独列出来，附原始消息文本、时间、频道，并指出 `signal_parser.py` 里是哪条规则没覆盖。这是每天最该看的一件事。

2. **实际成交质量**。每笔 OPEN：信号价 → 挂单限价 → `FILL_ADJUST` 后的真实成交价，算滑点。有没有挂出去没成交的？CLOSE 的同理，看 `pct` 字段（止盈百分比）。

3. **持仓状态**。停机时还有哪些 OPEN？其中哪些是**过期的/隔夜不该留的**（注意 `eod_force_close` 标记和期权到期日 —— option_code 里的 6 位是 YYMMDD）。有没有该强平但没平的？

4. **系统健康**。统计断线次数（`on_disconnect`）、有没有触发 `Discord storm` / `Discord churn`；Telegram 发送失败几次；有没有 traceback / `ERROR` / `exception`。掉线窗口和收到信号的时间点有没有重叠 —— 也就是说，有没有可能在盲区里漏了消息（注意 `_backfill_missed` 是否补上了）。

5. **今天要动的事**。最多 3 条，具体到文件和改法，按性价比排序。没有值得改的就直说"无"，不要凑数。
