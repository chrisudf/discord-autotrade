# 昨晚复盘的评判标准

这份文件是复盘的**唯一事实来源**。Claude 的定时任务 `autotrade-nightly-review`
每早读它来决定看什么、怎么写。想改复盘的关注点，改这里就行，不用碰定时任务本身。

调用方（定时任务）会先把这两份素材的具体路径告诉你：

- **整晚终端日志** `autotrade_YYYY-MM-DD_overnight.txt`
- **数据库摘要** `digest_YYYY-MM-DD.txt`（当晚开仓 / 事件流 / 下单记录 / 收到的全部原始消息 / 未平持仓，时间已转成本机本地时区）

要判断解析为什么失败就读 `autotrade/parsing/signal_parser.py` 和 `autotrade/listener/`。

**只用 Read / Glob / Grep 工具，不要调用 Bash。** 定时任务是无人值守跑的，
Bash 会触发权限确认，而那时没人去点 —— 实测卡死过一次（2026-08-05 早上，
一条 `ls` 把整个复盘挂了 2.5 小时）。摘要里已经有了当晚全部数据库记录，
正常复盘用不到 `sqlite3`。真需要更细的数据，就在回答里说明要查什么，
让人手动跑。

先把摘要整个读完，再读日志。日志可能有几千行，别一次全灌进来 —— 用 grep 按下面的
关键标记切片，只在需要确认上下文时才读原文附近几十行。

两个格式上的坑，先记住：

- 摘要是 `列 | 列 | 列` 的一行一条记录；原文里的换行已被压平成 ` / `。
- **喊单机器人每条消息都会发中英两遍**（相隔 2-4 秒，msg_id 不同）。统计条数时按语义
  去重，别把同一个信号算成两条。

## 要回答的问题

按重要性从高到低：

1. **漏掉的信号**（最重要）。grep `Parse failed` 和 `[parser] no signal`，逐条判断：
   哪些其实是**有效的开/平仓信号但解析器没认出来**？哪些确实只是闲聊/播报（例如喊单员的
   行情评论、盘前提醒、@everyone 通知），属于正确忽略？把前者单独列出来，附原始消息文本、
   时间、频道，并指出 `signal_parser.py` 里是哪条规则没覆盖。这是每天最该看的一件事。

2. **实际成交质量**。每笔 OPEN：信号价 → 挂单限价 → `FILL_ADJUST` 后的真实成交价，
   算滑点。有没有挂出去没成交的？CLOSE 同理，看 `pct` 字段（止盈百分比）。

3. **持仓状态**。停机时还有哪些 OPEN？其中哪些是**过期的/隔夜不该留的**（注意
   `eod_force_close` 标记和期权到期日 —— option_code 里的 6 位是 YYMMDD）。
   有没有该强平但没平的？

4. **系统健康**。统计断线次数（`on_disconnect`）、有没有触发 `Discord storm` /
   `Discord churn`；Telegram 发送失败几次；有没有 traceback / `ERROR` / `exception`。
   掉线窗口和收到信号的时间点有没有重叠 —— 也就是说，有没有可能在盲区里漏了消息
   （注意 `_backfill_missed` 是否补上了）。

5. **今天要动的事**。最多 3 条，具体到文件和改法，按性价比排序。没有值得改的就直说
   "无"，不要凑数。

## 输出

**输出到哪里由调用方指定** —— 这份文件只管内容和格式。现在有两个调用方：
Claude 的定时任务（要求直接在对话里回答）、`ops/opus_review.sh`（要求写成
markdown 文件）。别自作主张换地方。

结构：

```
## TL;DR
（3-5 个 bullet，把最该知道的说完。有漏单的话第一条必须是它。）

## 1. 漏掉的信号
## 2. 成交质量
## 3. 持仓状态
## 4. 系统健康
## 5. 今天建议做的
```

写作要求：

- 用中文。
- 所有时间用本地时间（摘要里已经是了），需要对照美股时段时在括号里补 ET。
- 数字要具体（几条、几点几分、滑点多少），不要"多次"、"若干"、"表现良好"这种词。
- 拿不准的事标成"待确认"并说明怎么验证，不要猜一个说法当结论。
- 昨晚要是根本没有信号也没有异常，回答就写得很短 —— 短是对的，不要为了凑篇幅注水。
- **不要修改仓库里的任何代码**，这是复盘不是施工。
